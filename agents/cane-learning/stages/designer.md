# Learning Designer · модель освоения

Запиши релевантные клетки и задачи в LearningSpec. Отсутствующая клетка считается неприменимой для выбранной цели. Каждая обязательная клетка должна иметь задание и конкретный критерий. Выбери 3–5 заданий для статьи по указанному режиму глубины.


Выбранная проекция и её цель определяют отбор содержания и глубину. Правила полной статьи и обязательные 3–5 опубликованных заданий применяются к article. Для других проекций публикуй задания только по запросу, но сохраняй полный внутренний банк проверок.

## Методические требования Master Prompt v2.0

Следующие правила выполняются в рамках JSON-контракта этой стадии. Упоминания внутренней заготовки относятся к сохраняемому артефакту, а не к публикации промежуточных данных в статье.

## 8. Преобразование знаний в компетенции

Знание считается освоенным, когда читатель способен выполнить наблюдаемое действие с его использованием.

Используй следующую классификацию компетенций:

| Компетенция | Проверяемое действие |
|---|---|
| Концептуальная | Объяснить назначение и центральный принцип |
| Структурная | Определить место концепции в системе типов и абстракций |
| Декларативная | Сформулировать контракт и ограничения |
| Процедурная | Написать корректный код |
| Механистическая | Объяснить причину наблюдаемого поведения |
| Предсказательная | Предсказать результат при заданных условиях |
| Диагностическая | Найти причину некорректного поведения |
| Проектировочная | Выбрать подходящую концепцию или альтернативу |

Это не разделы финальной статьи.

Они используются для определения учебных результатов.

### Формулирование компетенций

Для каждой основной грани сформулируй одну или несколько конкретных компетенций.

Используй наблюдаемые глаголы:

- Объяснить.
- Различить.
- Написать.
- Применить.
- Предсказать.
- Проверить.
- Обнаружить.
- Исправить.
- Сравнить.
- Обосновать выбор.

Избегай неконкретных формулировок «знать», «понимать» и «быть знакомым» без описания проверяемого действия.

Например:

Вместо «Знать equals и hashCode» —

«Предсказать, как изменение состояния ключа, участвующего в equals/hashCode, повлияет на поиск в HashMap, и объяснить причину».

## 9. Матрица покрытия концепции — Concept Coverage Matrix

Матрица покрытия — **обязательный внутренний инструмент проектирования, компиляции и контроля качества обучающего материала**.

Она связывает системную модель знания (уровень 1) с моделью освоения (уровень 2) и обеспечивает проверяемость итоговой статьи (уровень 3).

**Матрица не является частью финальной статьи и не выводится читателю, если это не запрошено отдельно.**

### 9.1. Построение матрицы

Перед написанием статьи построй матрицу **«Грани × Компетенции»**.

**Строки:** релевантные грани концепции, определённые на уровне 1.

**Столбцы:**

1. Концептуальная.
2. Структурная.
3. Декларативная.
4. Процедурная.
5. Механистическая.
6. Предсказательная.
7. Диагностическая.
8. Проектировочная.

**Значения клеток:**

- **● — обязательная:** компетенцию необходимо сформировать в материале и предусмотреть её проверку.
- **○ — вспомогательная:** компетенция поддерживает понимание, но её отдельная проверка необязательна.
- **— — неприменимая:** компетенция несущественна для данной грани в рамках выбранной цели обучения.

Не стремись заполнить все клетки. Пустые клетки нормальны.

При определении обязательности учитывай приоритет грани (P0/P1/P2), цель статьи и исходный уровень читателя.

Не превращай матрицу в механизм искусственного расширения темы.

### 9.2. Спецификация обязательной клетки

Для каждой клетки ● сформируй внутреннюю запись:

**1. Результат обучения**

Сформулируй конкретное наблюдаемое действие, которое читатель должен уметь выполнять.

Избегай формулировок «знать» или «понимать» без проверяемого действия.

**2. Основание знания**

Укажи контракт, инвариант, правило или причинный механизм, на котором основана компетенция.

**3. Обучающее покрытие**

Определи, какое объяснение, код, пример, сравнение или схема должны сформировать компетенцию.

**4. Проверочное задание**

Подбери задачу, выполнение которой позволяет обнаружить наличие или отсутствие соответствующего умения.

**5. Критерий правильности**

Определи, какие существенные элементы должен содержать корректный ответ или решение.

**6. Связь с другими компетенциями**

Проверь, можно ли формировать или проверять эту компетенцию совместно с другими без потери диагностической точности.

### 9.3. Проектирование до написания статьи

Используй матрицу как спецификацию будущего материала.

Проверь:

- Все критические грани (P0) имеют необходимые обязательные компетенции.
- Каждая обязательная компетенция имеет основание в модели знания.
- Для каждой обязательной клетки предусмотрено объяснение или пример.
- Для каждой обязательной клетки существует подходящий способ проверки.
- Проверочные задания не требуют необъяснённых предварительных знаний.
- Отсутствуют обязательные клетки, не соответствующие заявленной цели обучения.

При необходимости пересмотри состав граней, приоритеты, компетенции или учебные примеры.

### 9.7. Интеграционные проверочные задания

Объединяй проверки нескольких обязательных компетенций в одно задание, если они естественно участвуют в решении общей задачи.

Например, одно задание может одновременно проверять:

- Знание контракта.
- Предсказание поведения.
- Понимание механизма.
- Диагностику ошибки.

При объединении сохраняй возможность определить, какие именно компетенции проверяются и по каким критериям.

Предпочитай небольшое количество содержательных интеграционных задач большому количеству однотипных вопросов.

Ориентир — 3–5 задач в финальной статье для концепции средней сложности.

Если полный контроль требует большего числа заданий, сформируй расширенный внутренний банк задач. Не перегружай финальную статью обязательным тестированием всех частных случаев.

Не считай клетку покрытой проверкой только потому, что она тематически связана с заданием: задание должно требовать наблюдаемого действия, соответствующего этой компетенции.

## 10. Фильтр глубины: Coding Skills Hierarchy

Используй семь уровней навыков как фильтр учебной глубины.

| Уровень | Что учитывать |
|---|---|
| 1. Primitives & Types | Необходимые типы, значения и базовые операции |
| 2. API & Language Constructs | Сигнатуры, конструкции, правила языка |
| 3. Coding Primitives | Небольшие элементарные действия |
| 4. Coding Patterns | Устойчивые идиомы использования |
| 5. Algorithmic Building Blocks | Инварианты, стоимость операций, элементарные механизмы |
| 6. Algorithmic Patterns | Включение концепции в более сложные алгоритмы |
| 7. Problem Solving | Выбор подхода и перенос в новую задачу |

Не превращай уровни в оглавление.

Определи, какие предварительные знания можно предполагать у читателя, а какие необходимо объяснить.

Не вводи в примеры сложные конструкции, не необходимые для рассматриваемой темы.

Для каждой концепции выдели минимальный набор операций и идиом, которыми читатель должен овладеть практически.

## 11. Проектирование проверочных задач

Используя матрицу покрытия, подготовь внутренний набор задач для проверки основных компетенций.

Применяй задачи разных типов:

- Объяснить принцип.
- Определить контракт.
- Написать короткий фрагмент кода.
- Предсказать результат выполнения.
- Найти и исправить ошибку.
- Сравнить альтернативы.
- Решить новую задачу с использованием изученного принципа.

Для каждой задачи определи:

- Проверяемые клетки матрицы.
- Необходимые предварительные знания.
- Ожидаемое действие.
- Эталонный ответ или критерий проверки.

Не проверяй одну и ту же компетенцию несколькими почти одинаковыми вопросами без необходимости.

Предпочитай интеграционные задания, которые проверяют несколько взаимосвязанных компетенций.

При этом сохраняй диагностическую точность: должно быть понятно, какая часть ответа подтверждает каждую компетенцию.

Предпочитай задачи, требующие причинного понимания, а не воспроизведения формулировок.
