# Разбор решения

Применяй **после** того, как `run_tests.py` дал зелёный результат. Пока тесты
красные — разбирать нечего, там баг, и его ищет пользователь, а не ты.

Разбор идёт строго по этим пяти уровням, в этом порядке. Не перескакивай на
стиль, если сложность не та.

---

## Уровень 1 — Сложность (блокирующий)

1. **Спроси пользователя** оценить время и память своего решения. Целевую
   сложность из `target` до этого не произноси — иначе он просто соглашается с
   названной цифрой, и проверки не происходит. Это половина ценности упражнения.
2. Сравни его оценку с `target`:
   - **совпало** → «попадание», одна строка подтверждения, переходи на уровень 2;
   - **код в цель, оценён неверно** → разбери, что он не заметил (таблица ниже).
     Задача закрыта, но это ровно тот навык, который сыпется на интервью;
   - **код хуже цели** → назови цель и место потери сложности, верни писать
     дальше. **Эталон не показывай.** Задача не закрыта.

Что искать в питоновском коде:

| Выглядит невинно | На самом деле |
|---|---|
| `if x in nums` (список) | O(n) внутри цикла → O(n²) |
| `nums.index(x)` | O(n) |
| `list.pop(0)` / `list.insert(0, x)` | O(n) |
| `nums.remove(x)` в цикле | O(n) + порча индексов |
| `sorted(...)` там, где цель O(n) | O(n log n) |
| `s = s + c` в цикле по строке | O(n²) на конкатенациях |
| срез `nums[i:j]` внутри цикла | скрытое копирование O(n) |
| `Counter(window)` на каждом сдвиге окна | O(n·k) вместо O(n) |
| рекурсия без `@cache` на перекрывающихся подзадачах | экспонента |

По памяти: считается ли результат? Обычно нет — но `O(1) дополнительной
памяти` означает, что нельзя завести второй массив размера n.

## Уровень 2 — Соответствие паттерну

Реши: пользователь применил целевой паттерн или получил верный ответ мимо него?

- **Верно и тем паттерном** → отметь и иди на уровень 3.
- **Верно, но другим паттерном той же сложности** → это нормально, скажи это
  прямо. Покажи целевой как альтернативу и объясни, когда он лучше.
- **Верно, но «по-питоновски мимо задачи»** → отдельный разговор. Например,
  `str(x) == str(x)[::-1]` для `palindrome_number` или
  `sorted(arr, key=lambda v: abs(v - x))[:k]` для `find_k_closest_elements`:
  ответ правильный, но на интервью попросят решение, которое задача проверяет.
  Скажи: «это пройдёт, но интервьюер попросит без строк / за O(log n)».

Поле `trap` в `PROBLEMS.json` называет ровно то, на чём в этой задаче спотыкаются.
Проверь его в первую очередь.

## Уровень 3 — Граничные случаи

Тесты в банке их закрывают, но пользователь должен научиться **называть их сам**.
Спроси: «какие входы ты проверил бы, если бы тестов не было?»

Обязательный список:
- пустой вход (`[]`, `""`, `None` для узла)
- один элемент
- два элемента (минимум для two-pointers)
- все элементы одинаковые
- все отрицательные (ломает инициализацию нулём)
- ответа не существует (что возвращаем — `-1`, `[]`, `0`?)
- для in-place: не создал ли новый объект вместо мутации
- для связных списков: `None`, один узел, случайный цикл в ответе
- для сеток: одна строка, один столбец

## Уровень 4 — Питоновость

Только когда сложность и корректность в порядке.

Что предложить:
- `enumerate` вместо `range(len(...))`
- распаковка обмена: `a, b = b, a`
- `collections.Counter` / `defaultdict` вместо ручного `if k in d`
- `collections.deque` для очереди
- `functools.cache` для мемоизации
- `divmod` для «частное и остаток»
- `zip(nums, nums[1:])` для соседних пар
- осмысленные имена: `left/right`, `slow/fast`, `write/read` — а не `i/j/k`
- ранний выход вместо глубокой вложенности

Чего **не** делать: не превращай понятный цикл в непрозрачный однострочник.
На интервью читаемость важнее краткости.

---

## Уровень 5 — Как это звучит на интервью

Последний шаг, самый недооценённый. Попроси пользователя **проговорить решение
за 60 секунд**, как будто перед интервьюером. Хорошая формулировка содержит:

1. Переформулировку задачи своими словами.
2. Названный паттерн и **почему именно он** («массив отсортирован, значит…»).
3. Ключевой инвариант («слева от `write` всегда лежат уже отобранные элементы»).
4. Сложность по времени и памяти.
5. Один граничный случай, который он обработал отдельно.

Для greedy-задач пункт 2 обязателен в форме **доказательства**, а не «мне
кажется, так сработает».

---

## Что говорить, когда решение неверно

Не показывай эталон. Порядок действий:

1. Назови **конкретный провалившийся тест** из вывода харнесса.
2. Спроси: «прогони этот вход в голове — на каком шаге расходится?»
3. Если застрял — подсказка уровня 1, потом 2, потом 3
   (`run_tests.py --hint <id> --level N`).
4. Эталон (`--reference <id>`) — только после того, как пользователь либо решил,
   либо явно попросил показать.

Провал по таймауту — это почти всегда бесконечный цикл: не обновляется граница
в `while`, либо потеряна ссылка в связном списке. Скажи это прямо, там нечего
угадывать.
