# Workflow: retrospective

For a completed period (a finished Plan, a quarter, a milestone). Read-only
analysis — like `review`, it proposes, never applies.

## Questions to work through (spec §15 — keep all of them, don't skip to the
comfortable ones)

1. What produced Results? (read `Results` in the period, grouped by Plan)
2. What was Activity without Outcome? (Tasks completed with no matching Result —
   [rules/outcomes.md](../rules/outcomes.md))
3. Which Plans completed?
4. Which Plans stalled (still `status-active`, little/no recent Task activity)?
5. Why, as best the data + the user's own account shows — ask, don't assume.
6. Where was the wrong Priority set (Strategic or Operational — check both,
   they're different failure modes, [rules/priorities.md](../rules/priorities.md))?
7. Where was WIP excessive (periods where active-Plans count exceeded the limit)?
8. What recurring obstacles came up (look for repeated cancellation reasons,
   repeated deferrals of the same kind of Plan)?
9. What process changes are worth making (WIP limit itself, how Plans get
   scoped, Inbox triage cadence)?

## Boundaries

- Don't turn this into psychological coaching unless the user explicitly asks
  for that angle — stick to the process/outcome questions above.
- Any process change that comes out of this (new WIP limit, retiring a Goal,
  restructuring an Area) is proposed here and **applied through its own
  workflow's normal confirmation**, not written directly from retrospective.
